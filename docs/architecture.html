Architecture & Refactoring

How a single 600-line R script became a modular Shiny application

Before: Two monolithic scripts

The original codebase in original_scripts/ consisted of two files:

Main script (~624 lines)

Metropolis Sampling - 2022-01-01 v2a.R

  • Parameters, functions, simulation loop, data reshaping, and 10 plot types — all in one file
  • Single function annualizeFn() that reads int.period from global scope
  • Control flow via runCalcs flag and plotType integer switch (1–10)
  • Global state everywhere — variables assigned at top, mutated throughout
Meta script (~35 lines)

Metropolis Sampling - Meta Script - 2021-12-22 v1.R

  • Loops over allocations by setting perc.stocks globally then calling source() on the main script
  • Accumulates results via rbind() on globals
  • Requires commenting out set.seed(100) in the main script to avoid identical trajectories

After: Five modules with clear separation

R/ helpers.R -- Pure utility functions (unit conversion, string parsing, formatting) simulation_engine.R -- Core MCMC: covariance, interest, simulation loop, post-processing meta_sweep.R -- Frontier sweep loop (run_meta_sweep()) plotting.R -- All 8 plot_*() visualization functions theme_config.R -- Centralized color/size theme server.R -- Shiny reactivity only — delegates to R/ modules ui.R -- Shiny UI layout

Module responsibilities

helpers.R — Pure utility functions with no dependencies on other modules. Handles unit conversion (clamp_pct_to_fraction()), string parsing (parse_allocation_string()), and display formatting (format_summary_table(), format_params_summary()).

simulation_engine.R — The computational core. Contains build_covariance_matrix(), build_interest_vectors(), simulate_portfolios() (Metropolis-Hastings loop), build_result_dataframes(), compute_rolling_sd(), and compute_gain_summary(). Also provides run_simulation(), a coordinator that calls all sub-functions in sequence and returns a combined result list.

meta_sweep.R — Loops over a vector of stock allocations, calling run_simulation() for each. Collects point estimates for the frontier curve and per-simulation cloud data. Accepts a progress_callback for Shiny or console progress reporting.

plotting.R — Eight plot_*() functions, each producing a self-contained ggplot object. Covers gain-vs-SD scatter, trajectory fans, cost profiles, final densities, rebalancing deltas, single-sim explorer, efficient frontier, and frontier explorer.

theme_config.R — Single source of truth for the app's visual theme: colors, font sizes, and ggplot theme settings. All plotting functions reference this rather than hardcoding values.

Organizing principles

1.

Pure functions with explicit inputs/outputs. Every function takes all its inputs as arguments and returns results — no reading from or writing to global scope. The original annualizeFn() that implicitly used int.period is now a local call with all parameters passed explicitly.

2.

Coordinator pattern. run_simulation() orchestrates the sub-functions (covariance → interest → simulation → dataframes → rolling SD → gain summary) and returns a single result list. This keeps each sub-function focused while providing a convenient one-call entry point.

3.

Separation: engine → reshaping → visualization. The simulation engine produces raw arrays. Post-processing reshapes them into tidy data frames. Plotting functions consume those data frames. Each layer can be inspected independently.

4.

Shiny reactivity stays in server.R. The R/ modules have zero Shiny dependencies. server.R handles reactive inputs, calls the modules, and renders outputs. This means all functions are usable from a plain R console or RStudio session.

5.

Console-friendly by design. Functions work identically whether called from the Shiny app, an R console, or a batch script. The scripts/ directory demonstrates this with precomputation scripts that call the same functions the app uses.

Benefits

  • Inspect intermediates — Run each pipeline step in RStudio and examine the output: covariance matrices, interest vectors, raw simulation arrays, tidy data frames
  • Step through the pipeline — Debug by calling sub-functions one at a time rather than running a 600-line script end-to-end
  • Swap parameters — Change any input without editing source code; just pass different arguments
  • Run offline batch jobs — scripts/precompute_scenarios.R calls the same functions to precompute frontier data at high simulation counts
  • Test in isolation — Each function can be tested with known inputs without standing up the full Shiny app
