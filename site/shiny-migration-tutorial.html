From R Script to Shiny App

How a ~450-line monolithic R simulation was restructured into an interactive Shiny application — and why each change was made.

The Starting Point

The original code was two R scripts. The main script (~400 lines) mixed parameters, computation, and plotting in a single file. The second script (~30 lines) looped over allocation percentages by source()-ing the main script repeatedly.

Here's a condensed view of how the original main script was organized:

And the meta script — the efficient frontier sweep:

Key observation: The meta script works by setting a global variable (perc.stocks), then source()-ing the entire main script. The main script reads that global and runs everything — all the computation, all the data frame assembly. This is clever but fragile: every variable the main script creates lands in the global environment, and the meta script has to know which output variable to grab (gainsVsSD.point.estDf).

The Shiny File Structure

The same logic, split into seven focused files. Each file has a single responsibility. No globals, no side effects, no plotType switch.

r-shiny-portfolio/
├── global.R — loads packages, sources the R/ modules
├── ui.R — the user interface: sliders, buttons, tabs
├── server.R — reactive wiring: inputs → computation → outputs
└── R/
    ├── helpers.R — small utility functions
    ├── simulation_engine.R — core MCMC simulation (pure function)
    ├── meta_sweep.R — efficient frontier sweep
    └── plotting.R — one function per plot type
Why this structure? Shiny expects three files at the top level — global.R, ui.R, and server.R. Anything in the R/ subdirectory is conventional for helper code. This separation means you can edit a plot function without touching the simulation logic, or add a new UI input without modifying any computation code.

Strategy 1: Extract the Computation Engine

The single biggest change: wrapping the ~200 lines of computation in a pure function that takes parameters in and returns structured data out. No side effects. No global variables.

  # land in the global environment as side effects.

After — a pure function with explicit inputs and outputs
# simulation_engine.R

run_simulation <- function(n, s.mean, s.sd, b.mean, b.sd, s.b.corr,
                           init.inv, perc.stocks, rebal.interval,
                           s.int, b.int, int.period,
                           propStepDivisor, nSims, nSimsToRecord,
                           widthVal, progress_callback = NULL) {

  n <- n - 1

  # Compose interest covariance matrix
  sdVec <- c(s.sd, b.sd) / propStepDivisor
  sdM <- diag(sdVec)
  rho <- matrix(c(1, rep(s.b.corr, 2), 1), ncol = 2)
  s.b.cov <- sdM %*% rho %*% sdM

  # ... same computation, now inside a function ...

  # Return structured output — no globals
  list(
    costsDf = costsDf,
    valueDf = valueDf,
    sharesDf = sharesDf,
    value.totDf = value.totDf,
    gainVsSDDf = gainVsSDDf,
    gainsVsSD.point.estDf = gainsVsSD.point.estDf,
    deltaDf = deltaDf,
    mean.vecDf = mean.vecDf,
    params = list(n = n, s.mean = s.mean, ...)
  )
}
Why this matters: The original script creates dozens of variables in the global environment — costs, value.rebal.tot, gainVsSDDf, etc. — with no clear contract about which ones are "outputs." The function version returns a single named list. Every downstream consumer (plots, tables, the meta sweep) pulls from that list. Nothing leaks.

# plotting.R — each function takes the result list, returns a ggplot

plot_gain_vs_sd <- function(result) {
  p <- result$params
  ggplot(data = result$gainVsSDDf, aes(x = sd, y = gain, color = type)) +
    geom_point(alpha = 0.08) +
    geom_point(data = result$gainsVsSD.point.estDf,
               aes(x = sd, y = gain, fill = type),
               size = 3, shape = 21, color = "black", alpha = 0.8) +
    geom_hline(yintercept = c(p$s.int, p$b.int),
               linetype = "dashed", color = "darkblue", alpha = 0.3) +
    ylab("gain (annualized %)") +
    xlab("standard deviation") +
    ggtitle(paste0("Stocks / Bonds = ", round(p$perc.stocks * 100, 1),
                   "% / ", round((1 - p$perc.stocks) * 100, 1), "%")) +
    scale_y_continuous(labels = scales::percent) +
    theme_light()
}

plot_trajectories <- function(result, max_sims = 100) {
  df <- result$value.totDf[result$value.totDf$sim <= max_sims, ]
  ggplot(data = df,
         aes(x = time, y = val,
             group = interaction(type, sim), color = type)) +
    geom_line(alpha = 0.1) +
    ylab("portfolio value ($)") +
    ggtitle(paste0("Portfolio Trajectories (up to ", max_sims, " sims)")) +
    theme_light()
}

Key differences in the "after" version:

  • Each function receives data through result$... — no global variable access
  • Parameters like perc.stocks come from result$params, not the global scope
  • Commented-out zoom levels are gone — the user can zoom interactively
  • No plot(plt) call — Shiny's renderPlot handles that

Strategy 4: The Meta Script Becomes a Function

The second script — which source()-ed the main script in a loop to sweep across allocations — becomes a clean function that calls run_simulation() directly.

# meta_sweep.R
run_meta_sweep <- function(perc.stocks.vec, n, s.mean, s.sd, b.mean, b.sd,
                           s.b.corr, init.inv, rebal.interval,
                           s.int, b.int, int.period,
                           propStepDivisor, nSims, nSimsToRecord,
                           widthVal, progress_callback = NULL) {

  results <- list()

  for (k in seq_along(perc.stocks.vec)) {
    alloc <- perc.stocks.vec[k]

    # Build a progress callback that also reports allocation progress
    sim_cb <- NULL
    if (!is.null(progress_callback)) {
      sim_cb <- function(i, total, msg) {
        progress_callback(k, length(perc.stocks.vec), i, total,
                          paste0("Allocation ", k, "/", length(perc.stocks.vec),
                                 " (", round(alloc * 100), "% stocks): sim ",
                                 i, "/", total))
      }
    }

    res <- run_simulation(
      n = n, s.mean = s.mean, s.sd = s.sd, b.mean = b.mean, b.sd = b.sd,
      s.b.corr = s.b.corr, init.inv = init.inv, perc.stocks = alloc,
      rebal.interval = rebal.interval, s.int = s.int, b.int = b.int,
      int.period = int.period, propStepDivisor = propStepDivisor,
      nSims = nSims, nSimsToRecord = nSimsToRecord,
      widthVal = widthVal, progress_callback = sim_cb
    )

    pe <- res$gainsVsSD.point.estDf
    results[[k]] <- data.frame(
      allocation = alloc,
      rebal_gain = pe$gain[pe$type == "rebal"],
      rebal_sd   = pe$sd[pe$type == "rebal"],
      nonrebal_gain = pe$gain[pe$type == "nonrebal"],
      nonrebal_sd   = pe$sd[pe$type == "nonrebal"],
      s.int = s.int, b.int = b.int
    )
  }

  do.call(rbind, results)
}

The source() pattern is replaced by a direct function call. Instead of setting a global variable and hoping the sourced script reads it, every parameter is passed explicitly. And instead of picking output from the global environment (gainsVsSD.point.estDf), results come back as return values.

Strategy 5: Reactive Wiring

server.R is the "glue" layer. It reacts to button clicks, calls the computation functions, stores results, and feeds them to plot renderers. This is the Shiny-specific part — everything else is plain R. 

# server.R — the reactive glue
function(input, output, session) {

  # Reactive values: the single source of truth for results
  sim_result   <- reactiveVal(NULL)
  sweep_result <- reactiveVal(NULL)

  # When the user clicks "Run Simulation":
  observeEvent(input$run_single, {

    # Disable buttons during computation
    shinyjs::disable("run_single")
    shinyjs::disable("run_sweep")

    # Convert percentage slider to fraction, clamping extremes
    perc <- max(0.000001, min(0.999999, input$perc_stocks / 100))

    # Run with a progress bar
    withProgress(message = "Running simulation...", value = 0, {
      result <- run_simulation(
        n         = input$n_timesteps,
        s.mean    = input$s_mean,
        s.sd      = input$s_sd,
        # ... all other params from input$... ...
        progress_callback = function(i, total, msg) {
          setProgress(value = i / total, message = msg)
        }
      )
      sim_result(result)  # Store the result
    })

    shinyjs::enable("run_single")
    shinyjs::enable("run_sweep")
  })

  # Every plot just reads from sim_result() — when it updates,
  # all plots automatically re-render.

  output$plot_gain_sd <- renderPlot({
    req(sim_result())           # Wait until there's data
    plot_gain_vs_sd(sim_result())  # Call our pure plot function
  })

  output$plot_trajectories <- renderPlot({
    req(sim_result())
    plot_trajectories(sim_result())
  })

  # ... one renderPlot per tab ...
}
The key Shiny concepts here:

reactiveVal() — A container for a value that Shiny tracks. When you write sim_result(result), anything that reads sim_result() is automatically notified and re-renders.

observeEvent() — Runs code when a specific input changes (here, a button click). This replaces the runCalcs = TRUE flag.

req() — Short for "require." Silently halts rendering if there's no data yet — no errors on startup.

renderPlot() — Tells Shiny "this output is a plot, and here's how to make it." Shiny calls this function whenever its reactive dependencies change.

Strategy 6: Progress Reporting & UX

Monte Carlo simulations can run for minutes. The original script gave no feedback — you'd stare at the console. The Shiny version reports progress per-simulation, with nested reporting for the frontier sweep.

Before — silent loop
for (j in 1:nSims) {
  # ... runs for minutes with no output ...
  costs[1,1,j] = rtruncnorm(1, a=0.5, mean=s.mean, sd=s.sd)
  # ...
}
⟱
After — progress callbacks at two levels
# In run_simulation():
for (j in 1:nSims) {
  if (!is.null(progress_callback)) {
    progress_callback(j, nSims,
                      paste("Running simulation", j, "of", nSims))
  }
  # ... same computation ...
}

# In server.R — the callback updates a Shiny progress bar:
progress_callback = function(i, total, msg) {
  setProgress(value = i / total, message = msg)
}

# In meta_sweep — nested progress for the frontier sweep:
sim_cb <- function(i, total, msg) {
  progress_callback(k, length(perc.stocks.vec), i, total,
                    paste0("Allocation ", k, "/", length(perc.stocks.vec),
                           ": sim ", i, "/", total))
}

The progress callback is an optional parameter (progress_callback = NULL) so the simulation function works perfectly well without Shiny — you could call it from a plain R script and simply not pass a callback.

The Core Insight

Most of the migration work isn't Shiny-specific. It's good R refactoring: wrapping computation in functions, eliminating globals, making outputs explicit.

Of the seven files in the Shiny project, only three are Shiny-aware (global.R, ui.R, server.R). The other four — simulation_engine.R, meta_sweep.R, plotting.R, and helpers.R — are pure R. You could call them from a plain script, a notebook, or a unit test. They don't know Shiny exists.

That's the real payoff: the code became better R code, and Shiny is just the thin interactive layer on top.
